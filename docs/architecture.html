System Architecture

This document provides a detailed architectural description of the bsuppla static analysis framework.

Table of Contents

  • Design Goals
  • Component Overview
  • Detector Framework
  • Processing Pipeline
  • Trust Model
  • Extensibility

1. Design Goals

The architecture is driven by the following design requirements:

Goal Description Priority
Zero Execution Never execute any code from analyzed images Critical
Extensibility Support custom detection plugins without core modification High
Testability Each detector must be independently testable High
Offline Operation No network dependencies during analysis Medium
Minimal Dependencies Self-contained, no external services required Medium

3. Detector Framework

The detector framework implements the Open/Closed Principle: open for extension, closed for modification. This is achieved through a trait-based plugin architecture.

3.1 Core Traits

// core.rs

pub trait Detector: Send + Sync {
    fn name(&self) -> &'static str;
    fn detect(&self, ctx: &FileContext) -> Option<Finding>;
    fn severity(&self) -> Severity {
        Severity::Medium
    }
}

pub struct DetectorRegistry {
    detectors: Vec<Box<dyn Detector>>,
}

impl DetectorRegistry {
    pub fn register(&mut self, detector: Box<dyn Detector>);
    pub fn detect(&self, ctx: &FileContext) -> Vec<Finding>;
}

3.2 Detection Context

Each detector receives a FileContext containing pre-computed file attributes:

pub struct FileContext<'a> {
    pub path: &'a PathBuf,           // Absolute path
    pub relative_path: &'a PathBuf,   // Path relative to root
    pub mode: u32,                     // Unix permissions
    pub is_executable: bool,
    pub is_world_writable: bool,
    pub is_world_readable: bool,
    pub is_suid: bool,
    pub is_sgid: bool,
}

3.3 Finding Structure

pub struct Finding {
    pub kind: String,      // Detection type identifier
    pub path: PathBuf,      // File path
    pub detail: String,    // Human-readable details
    pub severity: Severity,// Critical/High/Medium/Low
}

pub enum Severity {
    Critical,  // Score: 5
    High,       // Score: 4
    Medium,     // Score: 3
    Low,        // Score: 2
}

3.4 Rule-Based Detectors

Most simple signals (a file matching a path/name pattern) need no struct and no trait impl. PathRule pairs a finding rule with a predicate — one line, directly in default_registry():

registry.register(Box::new(PathRule::new(
    "docker_socket_present",
    Severity::Critical,
    "docker socket exposed",
    |ctx| ctx.normalized_path() == "/var/run/docker.sock",
)));

3.5 Detector Categories

Category Detectors Analysis Method
Permissions SUID/SGID, World-Writable, Writable Dir, Hidden Unix permission bits
ELF Analysis Stripped, Static, Packed, Unusual Location ELF header/section parsing
Credentials Private Keys, Authorized Keys, Credential Files Path pattern + content inspection
Package Managers npm, pip, gem, apk configuration Config file content analysis
Risk Indicators Miners, Risky Tools, Startup Scripts Binary name pattern matching

4. Processing Pipeline

The analysis pipeline follows a strict sequence:

+------------------------+     +------------------------+
| Docker Image (.tar)    |     | Acquire (optional)     |
| Untrusted Input        |     | pipeline.rs -> docker  |
|                        |     | pull + save            |
+-----------+------------+     +-----------+------------+
            |                            |
            v                            v
+------------------------------------------+
| ingest/                                  |
| image.rs   manifest.json parsing         |
| manifest.rs manifest model               |
| layers.rs  locate_layers()  verification |
| extract.rs filesystem reconstruction     |
+---------------------+--------------------+
                      |
                      v
+------------------------------------------+
| scan/scanner.rs     walk_dir()           |
| registry built once, passed down walk    |
+---------------------+--------------------+
                      |
                      v
+------------------------------------------+
| detectors/          ctx = FileContext    |
| default_registry()  findings = detect()  |
+---------------------+--------------------+
                      |
                      v
+------------------------------------------+
| scan/ allowlist + baseline filtering     |
| scan/report.rs  output + suspicion level |
+------------------------------------------+

4.1 Stage Details

Stage 0: Acquisition (optional)

pipeline.rs calls docker pull and docker save to produce the image tar. Skippable via BSUPPLA_SKIP_DOCKER when scanning an existing tar.

Stage 1: Image Loading

Parses the Docker image tar archive using the tar crate (ingest/image.rs). Extracts manifest.json to identify layer paths.

Stage 2: Layer Verification

ingest/layers.rs verifies all referenced layers exist in the tar archive. Returns error if any layer is missing.

Stage 3: Filesystem Reconstruction

ingest/extract.rs extracts each layer's layer.tar in order. Later layers override earlier ones.

Stage 4: Directory Traversal

scan/scanner.rs builds a single DetectorRegistry (from detectors::default_registry()) and recursively walks the reconstructed filesystem. For each file:

  • Collects file metadata (permissions, size, type)
  • Builds FileContext
  • Passes context to each registered detector
  • Collects all findings

Stage 5: Report Generation

scan/report.rs applies allowlist filtering (scan/allowlist.rs), baseline comparison (scan/baseline.rs), and severity scoring. Outputs findings with suspicion level.

5. Trust Model

Security Assumption

The Docker image under analysis is treated as untrusted input. The analysis process must never execute any code from the image.

Component Trust Level Rationale
bsuppla Code Trusted Audited, version-controlled
Docker Image Untrusted External input, may be malicious
Analysis Output Trusted Generated by verified code

5.1 Security Boundaries

  • No Execution: Files are never opened with execute permissions
  • No Network: Analysis runs completely offline
  • Read-Only: Output directory is cleaned before each run
  • Isolated: Should run in containerized environment

6. Extensibility

Two ways to add a signal, both closed against modification of the scanning machinery (scan/, core.rs).

6.1 Simple path/name signal — one line

// In detectors/mod.rs, inside default_registry():
registry.register(Box::new(PathRule::new(
    "docker_socket_present",      // finding kind (allowlist/baseline key)
    Severity::Critical,           // Critical | High | Medium | Low
    "docker socket exposed",      // report detail
    |ctx| ctx.normalized_path() == "/var/run/docker.sock",
)));

6.2 Signal that inspects file contents — custom Detector

use crate::core::{Detector, FileContext, Finding, Severity};

pub struct MyCustomDetector;

impl Detector for MyCustomDetector {
    fn name(&self) -> &'static str {
        "my_custom_detection"
    }

    fn detect(&self, ctx: &FileContext) -> Option<Finding> {
        // Custom detection logic (ctx.path = real path, read bytes)
        if ctx.normalized_path().ends_with("/etc/thing") {
            Some(Finding::new(
                "my_custom_detection",
                ctx.relative_path.clone(),
                "details here".to_string(),
                Severity::High,
            ))
        } else {
            None
        }
    }
}

Register it (plus the module declaration at the top of detectors/mod.rs):

// In detectors/mod.rs
pub mod my_custom;

pub fn default_registry() -> DetectorRegistry {
    let mut registry = DetectorRegistry::new();
    // ... existing detectors ...
    registry.register(Box::new(my_custom::MyCustomDetector));
    registry
}

Because every type (Detector, DetectorRegistry, PathRule, all detector structs/factories) is public, custom registry composition never requires modifying the crate: build your own registry from bsuppla::core + bsuppla::detectors.

Full recipes with copy-paste examples live in docs/DEVELOPMENT.md.

7. Conclusions

The bsuppla architecture provides:

  • Safe static analysis without code execution
  • Extensible plugin system via trait composition
  • Independent testability of each detector
  • Clear separation of concerns
